# CTDP 计时与结束状态可信度设计

## 背景

本设计是项目改进计划的第一个独立批次，只处理两个直接破坏 CTDP 协议可信度的问题：

1. 主链目标时间到达后，界面只能确认完成，不能诚实记录失败并进入裁决。
2. 主链和辅助链加载后依靠每秒递减本地状态，窗口后台节流、系统休眠或设备时钟跳变后会与后端截止时间产生偏差。

后续数据库恢复、导出、RSIP、迁移和安全改造分别使用独立设计与实施计划，避免把多个子系统塞进一次高风险改动。

## 目标

- `expected_end_at`、`due_at` 和 `confirmation_due_at` 是倒计时的唯一时间真值。
- interval 只负责触发刷新，不累计时间，也不通过 `previous - 1` 推导当前剩余时间。
- 窗口恢复可见或重新获得焦点时立即校准。
- 主链到时后同时允许“确认主链完成”和“未完成，进入裁决”。
- 保持当前运行中可提前进入裁决的行为。
- 不改变链长、判例、裁决和预约的后端业务语义。

## 非目标

- 不引入后台常驻计时服务、WebSocket、Rust tick 推送或新的依赖。
- 不在本批次重做全局通知的阶段去重策略。
- 不改变辅助链预约和确认窗口的持续时长。
- 不重构整个会话页面或全局样式。
- 不处理完成/裁决按钮的提交锁；该项在后续交互可靠性批次实施。

## 方案比较

### 方案 A：绝对截止时间 + 前端重算（采用）

抽出纯函数，根据截止时间和当前时间计算非负整秒。页面每秒调用一次该函数，并在 `visibilitychange` 与 `focus` 时立即调用。

优点：

- 改动范围小，沿用现有后端时间字段。
- 系统休眠后第一次重新执行即可校准。
- 纯函数容易进行边界测试，不需要模拟真实计时器。
- 不新增运行时依赖或跨进程协议。

代价：

- 页面处于后台时视觉数字可能不逐秒刷新，但恢复可见时会立刻正确；协议状态仍由后端时间决定。

### 方案 B：Rust 定时器持续向 WebView 推送

由 Rust 管理计时并发送事件。

优点是可以集中管理计时；缺点是增加生命周期、窗口重建、事件去重和测试复杂度。当前后端已有稳定的绝对截止时间，因此没有必要。

### 方案 C：接入系统级任务调度

使用操作系统调度能力触发到时事件。

这更适合应用完全退出后仍必须执行的任务。本批次只要求已运行应用的显示与操作正确，系统级调度属于过度设计。

## 架构

新增一个无 React 依赖的时间工具模块，负责：

- 将 SQLite UTC 文本时间解析为毫秒时间戳。
- 根据目标时间与 `now` 计算向上取整、下限为零的剩余秒数。
- 对缺失或无法解析的目标时间返回明确的无效结果，而不是隐式显示零。

同时新增一个无 React 依赖的主链展示模型，用剩余秒数返回运行中或到时状态以及允许显示的操作。这样可以在不引入组件测试依赖的前提下，直接验证到时后的双操作规则。

`FocusSession` 保存当前 session，不再只在初始化时计算时间；其刷新函数始终读取 session 的 `expected_end_at`。

`AuxiliarySession` 继续根据当前 phase 选择 `due_at` 或 `confirmation_due_at`，但每次刷新都重新选择目标时间并计算剩余秒数。倒数到零后仍复用现有 phase 转换逻辑。

页面使用一个轻量 hook 或局部 effect 订阅：

- 每 1000 毫秒刷新一次。
- `document.visibilitychange`，且页面变为 visible 时刷新一次。
- `window.focus` 时刷新一次。

所有监听器和 interval 在 phase 改变或组件卸载时清理。

## 主链状态与交互

### 运行中，剩余时间大于零

- 显示当前倒计时。
- 显示“进入裁决”。
- 保持返回启动页入口。

### 到时，剩余时间等于零

- 状态显示“时间已到 / 等待确认”。
- 同时显示：
  - 主操作：“确认主链完成”。
  - 危险次操作：“未完成，进入裁决”。
- “未完成，进入裁决”调用现有 `setFocusSessionPendingRuling`，并进入现有裁决界面。

### 从裁决返回任务

- 立即按 `expected_end_at` 重算。
- 如果已经到时，返回到时后的双操作状态；不会重新出现正数倒计时。

## 辅助链状态

- `countdown` 阶段以 `due_at` 为目标。
- `confirming` 阶段以 `confirmation_due_at` 为目标；字段缺失时沿用当前 `due_at` 兼容逻辑。
- 到达预约截止时间后进入确认阶段，并立即按确认截止时间重算。
- 到达确认截止时间后调用现有到期逻辑进入待裁决。
- 休眠跨过一个或两个截止点时，恢复后必须根据页面持有的 session 截止时间收敛到正确阶段，不能再从旧的剩余秒数继续递减。

## 错误处理

- 非法时间字符串不能被当作“已经到时”。页面应进入现有错误展示路径，错误信息说明 session 截止时间无效。
- 刷新函数不能在错误后继续运行 interval。
- 本批次不吞掉新的解析错误。

## 测试

### 纯函数单元测试

- 截止时间在未来 1500 毫秒时返回 2 秒。
- 截止时间等于当前时间时返回 0。
- 截止时间已过去时返回 0。
- UTC SQLite 时间字符串按 UTC 解释。
- 无效时间字符串返回错误。

### 主链展示模型

- 剩余时间大于零时仅显示“进入裁决”。
- 剩余时间等于零时同时显示“确认主链完成”和“未完成，进入裁决”。
- 到时状态同时允许完成和裁决两个操作。

### 辅助链行为

- 预约阶段使用 `due_at`。
- 确认阶段使用 `confirmation_due_at`。
- 恢复可见时跨过预约截止时间会进入确认阶段。
- 恢复可见时跨过确认截止时间会进入待裁决。

### 回归检查

- 单元测试使用项目已有 TypeScript 编译器和 Node 内置测试能力，不增加测试依赖。
- 手工确认到时后点击“未完成，进入裁决”调用现有 pending-ruling 命令。
- 手工模拟从后台恢复后，显示值由绝对截止时间重新计算，不延续旧计数。
- Rust 现有测试不因前端计时调整而变化。
- TypeScript 类型检查、ESLint 和生产构建通过。
- 手工验证系统休眠后主链和辅助链页面恢复到正确时间与状态。

## 验收标准

1. 主链到时后可以完成，也可以进入裁决。
2. 主链和辅助链不再使用 `setRemaining(previous => previous - 1)` 作为计时依据。
3. 页面在 `visibilitychange` 和 `focus` 后立即按绝对截止时间校准。
4. 无效截止时间会显示错误，不会被误判为到时。
5. 既有裁决、完成、预约履约和链长行为保持不变。
6. 新增测试覆盖时间计算边界和到时双操作状态。
